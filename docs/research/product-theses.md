# Product theses — 소유자 논지와 반증 조건

- 작성 2026-11-26. 상태: **가설**. 결정이 아니며 `DECISIONS.md`를 대체하지 않는다.
- 목적: 설계·Goal 세션이 "무엇을 만들지" 판단할 때 참조하는 제약 목록.
- 규칙: 여기 적힌 것은 근거가 확인되기 전까지 사실로 인용하지 않는다. 각 항목의 반증 조건이 발생하면 폐기한다.
- 정본 관계: 결정은 `DECISIONS.md`, 아키텍처는 `docs/ARCHITECTURE.md`, 전략은 `docs/research/iskra-survival-strategy.md`다. 이 문서는 그 아래의 판단 제약이다.

## T1 — 소프트웨어는 도구로 내려가고, 가치는 지시 레이어로 올라간다

- **논지:** 에이전트가 소프트웨어를 호출하는 구조가 되면, 소프트웨어는 capability로 내려간다. 가치는 "무엇을 시킬지, 무엇을 허용할지, 결과가 참인지"를 쥔 레이어로 올라간다.
- **Iskra 함의:** Iskra는 봇·앱이 아니라 지시·권한·판정 레이어다. 표면은 `지시 → 실행 → 증거 판정` 세 동작이면 충분하다.
- **설계 제약:**
  1. 외부 API는 제출·상태/결과·증거 3개를 넘지 않는다. 도구 기능(검색, 스티키, 메모)을 API로 노출하지 않는다.
  2. Iskra가 소유하는 것은 identity·authority·acceptance·evidence·delivery다. 외부 소프트웨어는 adapter/capability로만 들어온다.
  3. 새 표면이 "또 하나의 도구"로 보이면 설계 실패로 본다.
- **반증:** 사용자가 지시 레이어에 비용을 내지 않고, 도구(앱) 기능에만 낸다.
- **현재 위험:** 공개 소개가 "개인용 텔레그램 봇"이라 스스로 도구로 보인다. 문구 수정은 G1~G3 이후 검증된 범위에서만 한다.

## T2 — 도입 병목은 거버넌스와 워크플로 통합이고, 그 병목은 솔로가 팔 수 없다

- **논지:** 모델 성능보다 도입 속도가 병목이다. ①거버넌스 프레임워크 수립 ②워크플로마다 다른 솔루션의 RFP·평가·리그레션(각 6개월 규모). 결과적으로 소프트웨어 간·에이전트 간 통합이 새 병목이 된다.
- **Iskra 함의:** 이 병목은 실재하지만 조달 주기가 길어 1인 개발자의 판매 대상이 아니다. 초기 표면은 **도입 결정이 필요 없는** 개인·소규모 팀 소유자를 겨냥한다.
- **설계 제약:**
  1. 정책 편집기·승인 워크플로 UI·RBAC·SSO·감사 리포트 대시보드를 만들지 않는다.
  2. 인증은 owner 토큰 1개, 바인드는 loopback. 조직·역할 개념을 넣지 않는다.
  3. 통합은 "기존 워크플로에 끼어드는 최소 표면"으로 한다. 새 워크플로 엔진을 만들지 않는다.
- **반증:** 엔터프라이즈 파일럿이 개인·소규모보다 먼저 실제 결제를 한다. 그때 표면을 다시 설계한다.
- **주의:** "엔터프라이즈를 영원히 안 한다"가 아니다. **초기 표면을 거기에 맞추지 않는다**는 뜻이다.

## T3 — Herdr류 호스트가 비워둔 것은 실행 안전성과 증거다

- **논지:** 터미널·에이전트 호스트는 layout·process·conversation 복원은 다루지만, 외부 부작용의 중복 실행·중복 전송 안전성은 별개 계층이다. Herdr 공개 문서도 서버 재시작 시 원래 프로세스가 살아나지 않는다고 명시한다.
- **Iskra 함의:** 경쟁은 기능 수가 아니라 `external-effect safety`에서 한다. 이건 Iskra가 이미 가진 것이다(무재실행, `unknown` 전달, `/result`).
- **설계 제약:**
  1. headless 표면도 "재시작 후 중복 실행 0건"을 1급 요구로 둔다.
  2. 세션 복원·터미널 UI·pane 관리는 범위 밖이다.
  3. Herdr 결함을 확정 사실로 주장하지 않는다. 공개 보고는 user report로만 인용한다.
- **반증:** Herdr 또는 인접 제품이 동등한 외부 부작용 안전성을 기본 제공하고, 사용자가 그걸로 충분하다고 판단한다.
- **출처:** `docs/research/iskra-survival-strategy.md` §11 (2026-11-25 조사).

## T4 — 작업 모델이 아니라 결과로 판정한다

- **논지:** "몇 번 돌았나"가 아니라 "원한 결과가 증거로 확인됐나"가 단위다. 모델의 완료 선언은 증거가 아니다.
- **Iskra 함의:** headless도 Run 완료가 아니라 acceptance 통과로 답한다. 이미 `docs/ARCHITECTURE.md`의 Outcome-first와 같은 방향이다.
- **설계 제약:**
  1. 증거는 exit code·파일 해시·Run/Delivery ID 같은 기계적 값만. 모델 판정 금지.
  2. outcome 필드는 이 슬라이스에 필요한 최소만. 6종 계약 일반화 금지.
  3. 값을 알 수 없으면 `unknown`으로 남긴다. 추정으로 채우지 않는다.
- **반증:** 고객이 acceptance 정의를 못 하고 "그냥 돌려줘"만 요구하며, 증거에 비용을 내지 않는다.
- **보강(2026-11-26 기록):** 사용자는 데이터 소유와 커스텀을 원한다. MCP처럼 요청한 것만 받는 방식보다 파일 전체 접근이 낫다는 관점. Iskra는 파일 네이티브·텔레메트리 0·1인 인스턴스로 이미 이 방향이다. 단 "커스텀"은 코드 수정이 아니라 `SOUL.md`·`USER.md`·`iskra.json`·스티키 같은 파일·프롬프트로 제공한다.

## 사용 규칙

- 설계 세션은 T1~T4를 **제약**으로만 쓴다. 논지를 새 기능 제안의 근거로 쓰지 않는다.
- 각 Task Card의 `Stop`에 해당 논지의 반증 조건을 연결한다.
- 이 문서는 `DECISIONS.md`보다 우선하지 않는다. 충돌하면 `DECISIONS.md`가 이긴다.
