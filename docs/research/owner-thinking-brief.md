## 1. 문제의식

- 모델 성능보다 도입 속도가 병목이다.
- 병목 ①거버넌스 프레임워크를 세우는 데 시간이 걸린다.
- 병목 ②워크플로마다 다른 솔루션을 RFP·평가·리그레션으로 들이는 데 각 6개월 규모. 결과적으로 소프트웨어 간·에이전트 간 통합이 새 병목이 된다.
- 엔터프라이즈 팀은 기존 스택 유지보수만으로 벅차서, 인하우스 바이브코딩을 스택에 끼워넣고 유지보수 대상만 늘리는 리스크를 지기 싫어한다.
- 그래서 off-the-shelf를 원하지만, 워크플로마다 에이전트가 따로 놀아 통합이 병목이 된다.

※ 6개월, "대부분 off-the-shelf 선호"는 소유자 관찰이며 출처가 확인되지 않았다.

## 2. 제품 논지 (가설)

| | 논지 | 설계 제약 |
|---|---|---|
| **T1** | 소프트웨어는 에이전트의 도구로 내려가고, 가치는 지시·권한·판정 레이어로 올라간다 | 외부 API 3개 이하, 도구 기능을 API로 노출하지 않음 |
| **T2** | 병목은 거버넌스·통합이며, 그 병목은 1인 개발자가 팔 시장이 아니다 | RBAC·SSO·정책 편집기·승인 UI·대시보드 금지, 개인·소규모 소유자만 |
| **T3** | Herdr류 호스트가 비워둔 것은 외부 부작용 안전성과 증거다 | 재시작 중복 실행 0건이 차별점, 터미널 UI·pane 복원은 범위 밖 |
| **T4** | 작업 모델이 아니라 결과로 판정한다. 모델의 완료 선언은 증거가 아니다 | exit code·해시·Run/Delivery ID만, 모르면 `unknown` |
| **T5** | 배포는 A(소스 있는 헤드리스 박스)와 B(1인 인스턴스)로 갈리고, Iskra는 A다 | 로컬 단일 바이너리 기본, 클라우드 전용 기능 금지, 커스텀은 파일·프롬프트 |

## 3. 소유자가 원하는 것 (인용 요지)

- 내 데이터를 내가 소유한다. MCP처럼 요청한 것만 받는 방식이 아니라 파일 전체 접근.
- 도구를 내 방식에 맞게 커스텀한다. 그건 프롬프트 하나면 된다.
- 정적 SaaS는 줄고, 소스를 사서 헤드리스 박스에 직접 돌리거나 1인 전용 인스턴스를 갖는 형태가 온다.
- 사람들은 이제 커스텀을 해보고 싶어 한다.
- 작업 모델이 아니라 결과 중심 개발.

## 4. 아직 논지가 아닌 것

- **Agent-Field 조사·리버스 엔지니어링**: 사실 조사 작업. 범위는 headless 표면(엔드포인트·인증·제출/조회 계약·재시작 처리·텔레메트리)만. 코드 복사 금지.
- **headless 집중**: 결정 사항. `DECISIONS.md` 2026-11-26.
- **Herdr**: `docs/research/iskra-survival-strategy.md` §11에 조사 기록이 있다.

## 5. 현재 결정 (재논의 금지)

- headless/v1 최소 슬라이스 선행. 감사 판매 트랙 보류(재개: G1~G3 완료 또는 2027-01-07).
- 범위: API 3개 이하, owner 토큰, loopback, 재시작 무재실행, 기계적 증거, `runs.json` 단일 실행 권한, 단일 테넌트, 텔레메트리 0, 로컬 단일 바이너리.
