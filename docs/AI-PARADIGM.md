# AI 패러다임 변화와 Iskra 적용 제안

작성일: 2026-11-23
상태: **사용자 제공 초안을 구조화한 전략 메모. 승인된 구현 계획이 아니다.**
기준선: 이 문서의 Iskra 현재 위치는 2026-11-23 저장소 상태를 기준으로 하며, 최신 상태는 `SESSION.md`, `SESSION-LOG.md`, `NOW.md`가 우선한다.

## 0. 이 문서를 읽는 기준

이 문서는 세 종류의 내용을 구분한다.

| 구분 | 의미 |
|---|---|
| 산업 가설 | AI 패러다임 변화에 대한 사용자 제공 전망. 별도 출처 검증 전에는 방향 판단용으로만 사용한다. |
| Iskra 현재 사실 | 저장소 코드·테스트·문서에서 확인된 상태. |
| Iskra 적용 제안 | 아직 구현되지 않은 후보. 별도 설계와 사용자 승인 없이는 착수하지 않는다. |

특히 원문에 적힌 `K3.1 Pro`, `K2.7 Code Highspeed` 등의 모델명은 현재 환경에서 실제 provider/model alias로 확인되지 않았다. 운영 문서에서는 모델명을 고정하지 않고 **역할**로 선택한다.

## 1. AI 패러다임의 진화 단계

### 1단계 — 사전 학습 중심

- 모델 파라미터와 학습 데이터를 늘려 지식을 암기하는 방식.
- 핵심 자원: 대규모 GPU, 전력, 고품질 텍스트·코드 데이터.
- 한계로 제기되는 것:
  - 고품질 학습 데이터 고갈.
  - 비용 대비 성능 향상의 수확 체감.
- 이 단계의 경쟁력은 모델 학습 자체에 있으므로 개인·소규모 팀이 직접 진입할 영역은 아니다.

### 2단계 — 추론 시점 확장

- 모델 크기보다 추론 시점의 반복 깊이를 늘린다.

```text
사고 -> 실행 -> 검증 -> 오류 수정 -> 재검증
```

- 관련 기반:
  - MoE, 양자화, KV 캐시 압축.
  - 코드·수학 샌드박스와 자동 검증기.
  - 검증 결과를 사용하는 강화학습과 추론 증류.
- 인프라 변화:
  - 초거대 단일 데이터센터와 온디바이스 실행의 병행.
  - 저전력 메모리와 SSD 오프로딩.
  - 빠르고 안전한 실행 샌드박스의 중요성 증가.
- 소프트웨어 기회:
  - 모델을 직접 학습하지 않아도 실행·검증·관제·기억 계층에서 가치를 만들 수 있다.

### 3단계 — 자율 실행과 지속 개선

- 단기 질의응답을 넘어 수일~수주 단위 작업을 계획·실행한다.
- 멀티 에이전트 협업, 장기 상태, 승인, 비용 상한, 재시작 복구가 필요하다.
- 실제 업무의 성공·실패 결과를 기억과 절차에 환류한다.
- **Iskra가 직접 겨냥할 현실적인 구간**이다. 단, 모델 가중치 자체를 실시간으로 학습하는 방식보다 코어 소유의 기억·절차·검증 기록을 축적하는 방식이 현재 구조와 맞다.

### 4단계 — 월드 모델과 피지컬 AI

- 물리 법칙과 복잡한 시스템의 인과관계를 시뮬레이션한다.
- 디지털 환경과 현실 세계의 행동을 연결한다.
- 막대한 데이터·연산·검증 인프라가 필요하다.
- Iskra v1~v3의 범위가 아니며, 별도 연구·제품 트랙으로 분리해야 한다.

## 2. 3·4단계를 대비한 소프트웨어 구축 영역

거대 모델 학습이 아니라 **에이전트가 안전하게 행동하고, 검증받고, 장기적으로 운영되는 소프트웨어 계층**이 기회다.

### A. 상태 저장형 실행 런타임

| 구성요소 | 필요한 이유 | Iskra 현재 상태 | 적용 판단 |
|---|---|---|---|
| 체크포인트·롤백 | 파일 수정·설치·명령 실행 후 실패 시 이전 상태로 복구 | 원자적 파일 쓰기와 세션 저장은 있으나 작업공간 전체 스냅샷은 없음 | Stage 2 이후 `checkpoint/v1` 후보 |
| 보안 프록시 | 실제 API 키·DB 자격증명을 에이전트에 노출하지 않고 외부에서 주입 | 비밀값 치환, 자식 환경 정리, OS 샌드박스는 있으나 외부 프록시는 없음 | 개인용 v1 범위 밖, 제품·팀 단계 후보 |
| 관제 대시보드 | 다수 실행의 상태·비용·정지·무한 루프를 관찰 | `/status`, 로그, usage 기록은 있으나 다중 실행 대시보드는 없음 | Stage 2 Run 상태 위에 Stage 4 로컬 UI로 확장 |

#### 체크포인트·롤백의 Iskra 제약

- 단일 바이너리·외부 DB 없음 원칙을 유지한다.
- 콘텐츠 해시와 파일 목록을 로컬에 저장하는 경량 `checkpoint/v1`부터 검토한다.
- 전체 홈 디렉터리가 아니라 승인된 Agent workspace만 대상으로 한다.
- 보존 개수·용량·기간 상한을 둔다.
- 롤백은 자동 재실행이 아니라 **소유자 승인 후 새 Run**으로 수행한다.
- 결제·외부 발송·비밀값 저장소는 스냅샷 대상이 아니다.

### B. 자동 검증기와 시뮬레이션 환경

| 구성요소 | 필요한 이유 | Iskra 현재 상태 | 적용 판단 |
|---|---|---|---|
| 결정론적 검증 파이프라인 | 테스트·빌드·API·DB·UI 결과를 구조화된 성공/실패로 반환 | 기존 테스트, `run_command`, SESSION 게이트가 사람이 읽는 형태로 존재 | 구조화된 `verification/v1` 후보 |
| 도메인 특화 가상 환경 | 실제 서비스 복제 환경에서 예외를 반복 학습 | 없음. watchpost와 파일럿 검증이 가장 가까운 소규모 사례 | 별도 제품·연구 트랙 |
| 에피소드 메모리 | 실패 로그와 해결 패턴을 후속 작업에 자동 주입 | Markdown 기억과 `session/v1`은 있으나 Graph/Vector 검색은 없음 | `procedure/v1` 실패 플레이북을 먼저 검토 |

#### 검증기 우선 원칙

1. 검증 결과는 자유 서술이 아니라 구조화한다.

```text
command
exit_code
duration
artifacts
failed_check
evidence_path
owner_only
```

2. 자동 검증과 소유자 검증을 분리한다.
   - 자동: 테스트, 빌드, 정적 검사, 파일·프로세스 상태.
   - 소유자: Telegram 실제 수신, 외부 provider, 화면 확인, 계정 상태.
3. `/goal`은 자동 검증이 가능한 작업에만 사용한다.
4. 실패 결과는 재시도 가능한 실패와 결정이 필요한 실패로 구분한다.

#### 메모리 확장 순서

현재 구조에서는 Graph/Vector DB를 코어에 넣는 것보다 다음 순서가 맞다.

1. Markdown 기억과 세션의 구조화.
2. 반복 실패·해결 절차를 `procedure/v1`로 축적.
3. 검색 필요가 측정되면 별도 프로세스 또는 선택 부품으로 인덱스 추가.
4. 코어에는 인덱스 구현을 고정하지 않고 검색 인터페이스만 둔다.

### C. 디지털 트윈과 인과관계 시뮬레이션

| 구성요소 | 적용 판단 |
|---|---|
| 비즈니스·시스템 월드 시뮬레이터 | Iskra 코어가 아니라 별도 제품·연구 트랙 |
| 엣지 케이스 시나리오 생성기 | watchpost의 장애 주입·자동화 감시와 접점은 있으나 아직 제품 범위 아님 |
| 3D/WebGL 상태 시각화 | 로컬 웹 UI 이후 별도 검토. v1~v3 코어 범위 밖 |

월드 모델 계층은 다음 조건 전에는 Iskra에 결합하지 않는다.

- 실제 사용자가 반복적으로 요청하는 검증 문제가 확인될 것.
- 시뮬레이션 정확도와 비용을 측정할 수 있을 것.
- 코어 바이너리·의존성·보안 예산을 침범하지 않을 것.
- 실패 시 실제 부작용이 발생하지 않는 샌드박스일 것.

## 3. Iskra의 현재 위치

Iskra는 1단계 모델 학습자가 아니라 **2단계 실행 도구에서 3단계 장기 실행 런타임으로 이동하는 단계**다.

현재 저장소의 승인된 방향:

- 모델 중립 실행 엔진.
- 코어가 기억·세션·정책·승인·감사·비용을 소유.
- fail-closed 권한과 명시적 Agent/Engine/Run 경계.
- 단일 바이너리, 로컬 데이터, 외부 DB 서버 없음.
- Stage 1에서 Engine·RunContext·Instance 경계와 Supervisor를 구축.
- Stage 2에서 두 개의 내장 HTTP Agent, 명시적 `@agent`, 독립 상태, FIFO, 제한된 동시 실행.
- ACP·자동 라우팅·자유 위임·호스팅은 별도 게이트.

따라서 A/B/C 전체를 한꺼번에 넣는 것이 아니라 다음처럼 흡수한다.

```text
Stage 1~2  실행·상태·격리 기반
Stage 3    ACP와 제한된 위임
Stage 4    검증·절차·로컬 UI·제품 표면
별도 트랙  Software Gym, 월드 모델, 3D 시뮬레이션
```

## 4. Iskra 적용 우선순위

### P0 — 현재 Stage 완료

- Stage 1의 Engine/RunContext/Instance/Supervisor 경계를 완료한다.
- Stage 2의 두 Agent 수직 슬라이스를 먼저 끝낸다.
- 이 문서의 아이디어를 이유로 현재 Stage 범위를 넓히지 않는다.
- 새 의존성, DB, 컨테이너, 웹 UI를 선행 도입하지 않는다.

### P1 — 검증과 복구 기반

Stage 2 완료 후 가장 먼저 검토할 후보:

1. **`verification/v1`**
   - 테스트·빌드·정적 검사 결과를 구조화.
   - `/goal` 완료 판정과 SESSION 기록에 같은 결과 사용.
   - 소유자 전용 검증을 명시적으로 분리.

2. **`checkpoint/v1`**
   - Agent workspace의 수정 전 스냅샷.
   - 콘텐츠 해시·보존 상한·원자적 복원.
   - 자동 롤백이 아니라 승인된 복구 Run.

### P2 — 운영과 제품 표면

- Run 상태·비용·정지·승인 대기를 보여주는 로컬 관제 UI.
- Agent별 workspace·도구·비용의 시각화.
- 제품 단계에서만 자격증명 프록시 검토.
- 외부 엔진은 ACP 게이트와 약관 검증 후 제한적으로 연결.

### P3 — 별도 연구 트랙

- Software Gym.
- 실패 시나리오 생성.
- 비즈니스 디지털 트윈.
- 3D/WebGL 시뮬레이션.
- 피지컬 AI.

이 항목들은 Iskra 코어의 로드맵과 분리하고, 독립적인 검증 제품이 생길 때만 연결한다.

## 5. Kimi Code 작업 운영 원칙

원문의 운영 아이디어를 현재 Iskra 워크플로에 맞게 적용한다.

### 원칙

> **큰 설계는 한 번, 구현은 작은 Goal, 사람 검증은 일반 모드.**

- 대형 설계를 구현 단계마다 다시 만들지 않는다.
- 큰 설계의 정본은 `docs/ARCHITECTURE.md`와 승인된 Stage 문서다.
- 해결되지 않은 실제 선택지만 Plan mode에서 다룬다.
- 구현 Goal은 자동 검증이 가능해야 한다.
- Telegram·실제 provider·화면 확인은 Goal 밖에서 소유자가 수행한다.
- 커밋·푸시는 Stage 또는 의미 있는 검토 지점에서 소유자 승인 후 수행한다.

### 모델 역할

모델명을 문서에 고정하지 않고 역할로 선택한다.

| 역할 | 선택 기준 | 사용 작업 |
|---|---|---|
| 계획·검토 모델 | 현재 사용 가능한 모델 중 추론·설계 품질이 가장 높은 모델 | 아키텍처, 보안 경계, 원인 분석, 최종 검수 |
| 실행 모델 | 현재 검증된 빠르고 비용 효율적인 모델 | 파일·테스트·합격 기준이 확정된 구현 |
| 소유자 | 사람 | 실사용 승인, 계정·외부 상태, 최종 판단 |

원문의 `K3.1 Pro`, `K2.7 Code Highspeed`는 예시 표기로만 남긴다. 실제 세션에서는 `/model` 또는 모델 선택기에서 **현재 계정에 표시되는 정확한 alias**를 확인해 사용한다.

### 1. 큰 설계

```text
/plan
```

Plan mode에서 다음을 확정한다.

- 결과와 현재 상태.
- Stage 경계와 비목표.
- 상태 전이와 보안 경계.
- 자동 검증과 소유자 검증.
- 정본 문서 경로와 Git 기준선.
- 아직 해결되지 않은 결정.

결과를 `docs/ARCHITECTURE.md`, Stage 문서, `SESSION.md` 중 올바른 정본에 반영한다.

### 2. 세션 작업 계획

세션 내부 작업 파일이 필요하면 `PLAN.md`를 사용할 수 있다.

```text
Outcome:
Spec:
Files:
Proof:
Current:
Stop:
Live:
```

`PLAN.md`는 작업 보조물이다. 프로젝트의 영구 정본이 되어서는 안 된다. 새 결정은 기존 프로젝트 문서에 반영한다.

### 3. 컨텍스트 초기화

```text
/clear
```

`/clear`는 `/new`의 별칭이며 현재 대화를 버리고 같은 작업 환경에서 새 세션을 시작한다. 파일·Git 상태·프로젝트 문서는 유지된다.

큰 설계 대화를 그대로 이어가는 대신:

1. 필요한 결정을 파일에 저장한다.
2. `/clear`로 대화 컨텍스트를 초기화한다.
3. 새 세션에서 `@PLAN.md`와 관련 정본 문서를 참조한다.

대화 맥락 일부를 유지해야 한다면 `/clear` 대신 `/compact [보존 지시]`를 사용한다.

### 4. 구현 모델로 전환

```text
/model
```

새 세션에서 실행 모델을 선택한다. 모델을 바꿔도 공통 기억, AGENTS, Git 상태와 파일은 유지된다.

### 5. Goal 실행

```text
@PLAN.md @docs/ARCHITECTURE.md @SESSION.md

Implement <Stage/item>.
Done when <command> produces <exact result>.
Only <allowed paths> may change.
Exclude <later stages, dependencies, external effects, commit/push>.
Run focused checks while iterating and the full milestone verification once at the end.
Stop on <missing decision, owner input, two failed approaches>.
Do not claim owner-only live verification.
```

```text
/goal 위 구현을 실행해
```

Goal에는 다음이 포함돼야 한다.

- 하나의 구현 주제.
- 기존 자동 검증.
- 허용·금지 경로.
- 실패 시 중단 조건.
- 소유자 입력이 필요 없는 완료 조건.
- 커밋·푸시 제외.

### 6. 소유자 검증

다음은 Goal에 넣지 않는다.

- Telegram 실제 수신.
- 실제 provider 과금·응답.
- 계정 설정.
- 화면·디자인 주관 판단.
- 외부 발송 승인.

일반 모드에서 체크리스트를 한 번 수행하고 결과를 `SESSION-LOG.md`에 기록한다.

## 6. 토큰·시간 최적화 규칙

1. 큰 설계를 구현마다 반복하지 않는다.
2. 확정된 task card가 있으면 작은 Plan 문서를 다시 만들지 않는다.
3. `/clear`는 대화 초기화 수단이지 프로젝트 기억 삭제가 아니다.
4. Goal은 하나의 자동 검증 가능한 주제만 가진다.
5. 반복 중에는 가장 작은 테스트만, milestone에서 전체 검증을 한 번 수행한다.
6. 이미 통과한 검사를 성공 보고만을 위해 반복하지 않는다.
7. 소유자 검증을 Goal 안에 넣어 자동 재개 루프를 만들지 않는다.
8. 실패가 2회 반복되면 접근을 바꾸고 원인을 기록한다.
9. 새 의존성·DB·UI는 현재 Stage의 검증을 돕는다는 증거가 있을 때만 검토한다.
10. 커밋·푸시는 자동화하지 않는다.

## 7. 도입 판단 체크리스트

새 아이디어를 Iskra에 넣기 전에 묻는다.

- [ ] 현재 Stage의 사용자 가치를 직접 높이는가?
- [ ] Iskra의 실제 실패·측정 결과가 이 기능을 요구하는가?
- [ ] 자동 검증 방법이 있는가?
- [ ] 실패 시 부작용과 롤백 경로가 명확한가?
- [ ] 비밀값·개인정보·권한 경계를 약화하지 않는가?
- [ ] 단일 바이너리·의존성·메모리 예산을 지키는가?
- [ ] 외부 DB·컨테이너·필수 클라우드 없이 동작하는가?
- [ ] 소유자 승인과 감사 기록이 남는가?
- [ ] 나중에 제거하거나 교체할 수 있는 부품 경계인가?
- [ ] 이번 Stage의 비목표를 침범하지 않는가?

하나라도 설명하지 못하면 구현하지 않고 설계 후보로만 기록한다.

## 8. 결론

Iskra의 차세대 기회는 거대 모델을 직접 학습하는 데 있지 않다.

> **모델이 바뀌어도 유지되는 기억·권한·검증·복구·실행 상태를 코어가 소유하고, 외부 모델과 엔진은 교체 가능한 부품으로 두는 것.**

우선순위는 다음 한 줄로 유지한다.

```text
현재 Stage 완료
-> 구조화된 검증
-> 작업공간 체크포인트·복구
-> 다중 Agent 관제
-> 제품 표면
-> 시뮬레이션·월드 모델은 별도 트랙
```
